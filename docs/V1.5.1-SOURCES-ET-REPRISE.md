# V1.5.1 — Sources, compilation et reprise

Le projet existant est conservé. Les archives V1.5.0 restent à la racine. Les sources courantes sont dans backend/, frontend/, tests/ et sql/. Le paquet sources V1.5.1 exclut les configurations privées, clés, secrets et données SQL importées ; son backend/wwwroot contient le frontend V1.5.1 compilé.

## Compiler localement
Avec SDK .NET 10 et Node/npm déjà installés, depuis le dossier du projet :

```powershell
cd C:\logista_zaouia
node frontend/node_modules/typescript/bin/tsc -b frontend
node tools/build-frontend-low-memory.mjs
dotnet publish backend -c Release -o publish-v151-tests --disable-build-servers -p:UseSharedCompilation=false -m:1
```

Sur ce poste le SDK privé existe dans `.dotnet\dotnet.exe` ; utiliser ce chemin à la place de `dotnet` si nécessaire. Le script de build web utilise les dépendances du package-lock conservé. Sur un nouvel environnement, installer ces dépendances dans frontend/ avec `npm ci`. Ne jamais copier une configuration de production dans l’archive sources.

Le script `tools/pack-v151.py` prend le frontend dans frontend/dist, le backend dans publish-v151-tests, vérifie les dépendances et la conservation Drencher, puis construit une copie additive update/. Il ne publie pas sur un site IIS.

## Environnement de test seulement
Les scripts refusent les configurations distantes. MySQL autorisé : **127.0.0.1:33307**, API : **127.0.0.1:5080**. Les VM ne doivent jamais être utilisées pour les tests transactionnels.

- `tools/prepare-v151-local.py` vérifie deux fois les migrations 013/014 dans l’administration locale seulement.
- `tools/prepare-v151-anomalies.py` prépare un petit jeu d’anomalies dans une base vitasouss_test_v151_invalid distincte ; aucune copie auditée n’est modifiée.
- `tests/AnalyticsV151Tests` vérifie les services et requêtes réelles.
- `tools/verify-v151-api.mjs` vérifie les nouveaux endpoints HTTP et droits.
- `tools/verify-v151-ui.mjs` effectue des rendus React/Mantine SSR et vérifie les choix visibles ; ce ne sont pas des captures navigateur.
- `tools/verify-v151-excel.py` relit les exports service et HTTP.
- `tests/DrencherV151Regression`, `tools/verify-drencher-v151-api.mjs`, `tools/verify-drencher-v151-guard.mjs` couvrent les permissions et transactions Drencher.
- `tests/AssistantTests` accepte un chemin de rapport JSON ; fournisseur fictif et zéro appel réel OpenAI.

Les tests HTTP attendent le mot de passe du compte **applicatif local de test**, via `VITASOUSS_TEST_PASSWORD`. Ce n’est pas une clé OpenAI. Ne jamais utiliser un compte de VM/production, ne pas écrire cette valeur dans les scripts ou paquets. Respecter la fenêtre du limiteur de connexions ; ne pas le désactiver.

Les données des bases synthétiques restent conservées pour inspection. Les comptes/contextes créés par les tests sont désactivés de façon ciblée ; `tools/cleanup-v151-local-fixtures.py` peut terminer ce nettoyage administratif local sans supprimer de données. Aucun nettoyage automatique sur une VM.

## Reprise après interruption
Lire d’abord **V1.5.1-ETAT-REPRISE.md**, puis les derniers rapports tests-v151-*.json. Vérifier /api/health avant de relancer les tests HTTP. L’API a déjà été relancée sur V1.5.1 ; les changements frontend ultérieurs ne nécessitent qu’un rafraîchissement navigateur.

Tant que l’accès navigateur à 127.0.0.1:5080 reste refusé par la préférence enregistrée, ne pas essayer d’autre navigateur ou d’outil indirect pour contourner. La revue visuelle et les captures doivent attendre sa réactivation par l’utilisateur.

La fabrication sans argument produit un **CANDIDAT**. `tools/pack-v151.py --final` exige les suites HTTP, Drencher et un rapport de revue visuelle avec au moins trois captures réelles enregistrées dans docs/. Ne jamais fabriquer ce rapport ou assimiler le SSR à une validation visuelle. Après fabrication, vérifier avec `tools/verify-v151-package.py` (ajouter `--final` pour le paquet définitif).
