# VITASOUSS V1.5.1 — Mise à jour depuis V1.5.0

Ce guide décrit une installation manuelle **après validation du candidat et des tests restants**. Aucun script de ce paquet ne déploie sur les VM. Base requise : VITASOUSS V1.5.0 + Drencher V1.3.2.1, déjà installé et fonctionnel.

## Sauvegarder
Sauvegarder le dossier IIS complet `C:\Apps\VitasoussReferentiels` et la base administrative `referentiels_admin`. Conserver appsettings.Local.json, web.config, clés Data Protection, secrets MySQL/OpenAI, identité svc_vitasouss, configurations IIS, utilisateurs et autorisations. Sauvegarder aussi les valeurs des contextes pour conserver leur visibilité lors d’un éventuel retour arrière.

Ne pas réexécuter les anciennes migrations Drencher, ne pas réinitialiser les réservations ou mouvements. Aucun SQL métier nécessaire.

## SQL séparé et explicite
Faire relire puis exécuter manuellement, **dans referentiels_admin uniquement**, dans cet ordre :

1. `sql/013-context-visibility.sql` : colonne de visibilité, défaut visible. Aucune permission modifiée.
2. `sql/014-crate-openings-admin.sql` : deux tables administratives d’inventaires versionnés. Aucune ouverture créée automatiquement.

Les deux scripts sont idempotents et ont été exécutés deux fois sur MySQL 5.7 local. Ils ne sont jamais lancés au démarrage de l’application. Le compte SQL d’exécution doit pouvoir ALTER/CREATE dans l’administration ; ne pas étendre les droits SQL métier du compte IIS. Les nouvelles tables reprennent les accès administratifs déjà configurés. MySQL 5.7 n’applique pas les CHECK : les validations sont imposées par l’API.

Sans SQL013, les consultations restent disponibles mais l’enregistrement d’un contexte demande la migration. Sans SQL014, les tableaux de bord restent disponibles et l’écran d’inventaire indique la migration manquante.

## Copier le correctif IIS
Sur VM-APPS, durant une maintenance, arrêter uniquement le pool IIS de VITASOUSS par l’outil IIS habituel. Décompresser le paquet dans un dossier temporaire distinct du site. Copier **le contenu de update/** dans `C:\Apps\VitasoussReferentiels` en remplaçant seulement les fichiers présents dans update.

**Copie additive uniquement : aucun /MIR, aucun effacement de dossier.** Le correctif contient seulement les quatre fichiers Vitasouss.Api et les nouveaux fichiers web compilés. Il n’inclut ni configuration locale, ni web.config, ni clé, ni secret, ni librairie tierce modifiée. Conserver les anciennes bibliothèques, ressources PDF et configurations.

Redémarrer le même pool sous la même identité svc_vitasouss. Ne pas créer de nouveau site ou changer le port 8081. Rafraîchir le navigateur pour charger les nouveaux fichiers web.

## Vérification après installation (par l’exploitant)
- `/api/health` : V1.5.1, Drencher 1.3.2.1.
- Réceptions : comparer les totaux aux rapports V1.5.0 sur la même période ; tester les onglets, filtres repliables et Excel.
- Caisserie : E/S et variation par type ; aucun stock/dette non justifié affiché.
- Administration : masquer puis réafficher un contexte de test ; contrôler le repli du sélecteur. Vérifier que les droits restent identiques.
- Inventaire : utiliser uniquement un exercice de recette pour le premier essai, confirmer les quantités, voir la nouvelle révision et l’auteur. Aucun solde courant certifié automatique.
- Drencher : Hicham saisie brouillon/soumission ; Mbark/Samira qualité/programmes ; impressions F04 et cinq documents de stock inchangés.
- Tester le mobile, le menu compact et les thèmes clair/sombre.

## Retour arrière
Arrêter le même pool, restaurer les quatre fichiers applicatifs et les fichiers web de la sauvegarde V1.5.0, puis redémarrer. Conserver les tables et colonne nouvelles : V1.5.0 les ignore. Ne pas supprimer les inventaires historiques enregistrés. La V1.5.0 affiche de nouveau tous ses contextes activés/autorisés, puisqu’elle ne connaît pas le masquage ; les droits n’ont pas changé.

Restaurer une sauvegarde SQL complète seulement si une procédure de reprise validée le nécessite, en évaluant toutes les écritures administratives intervenues depuis la sauvegarde. Aucun DROP/DÉLETE de données n’est nécessaire au retour arrière applicatif.

## Éléments non validés automatiquement
Les VM/IIS de production ne sont jamais contactées. DIAF et archives réelles doivent être contrôlées après installation sur des périodes connues. La certification des stocks/dettes attend la validation de nature, propriété, ouvertures et exhaustivité des mouvements. Lire le rapport de tests pour les captures/HTTP encore en attente si le paquet porte la mention CANDIDAT.
